# Understanding the Release Folder

## What You'll Learn

How the `release/` folder structure organizes release artifacts and how module contracts link to changelog files.

---

## Release Folder Structure

The repository uses a centralized `release/` folder to store all release-related artifacts:

```text
release/
├── r2r-cli/
│   ├── CHANGELOG.md
│   └── RELEASE-NOTES.md
├── ext-eac/
│   ├── CHANGELOG.md
│   └── RELEASE-NOTES.md
├── books/
│   └── CHANGELOG.md
└── r2r-eac-bundle/
    └── CHANGELOG.md
```

**Why centralized?**

- **Easy discovery**: All release artifacts in one place
- **Clear ownership**: One folder per module
- **Simple automation**: CI can find all changelogs by pattern matching
- **Audit trail**: Git history shows all release activities together

---

## Two Types of Release Files

Each module folder can contain two types of files:

### CHANGELOG.md (Technical Changes)

**Purpose**: Document technical changes for developers and users

**Format**: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) standard

**Structure**:

```markdown
# Changelog

All notable changes to **module-name** will be documented in this file.

## [Unreleased]

## [1.2.4] - 2026-01-15

### Added

- feat: new configuration validation command
- feat: support for custom templates

### Fixed

- fix: handle empty files correctly in parser

## [1.2.3] - 2026-01-10

...
```

**Categories**:

- **Added**: New features
- **Changed**: Changes to existing functionality
- **Deprecated**: Soon-to-be removed features
- **Removed**: Removed features
- **Fixed**: Bug fixes
- **Security**: Security updates

**Generated by**: `r2r release this <module>` from conventional commits

**Used by**:

- Developers understanding what changed
- Users reviewing release notes
- CI determining next version number
- GitHub releases content

### RELEASE-NOTES.md (Release Assessment)

**Purpose**: Business and compliance assessment of releases

**Format**: Custom format for fitness assessment

**Structure**:

```markdown
# Release Notes

## [1.2.4] - 2026-01-15

### Summary

Brief description of the release purpose and scope.

### Conclusion on Fitness for Intended Use

Assessment of whether the release meets requirements and is fit for production use.

### Impact on Business Process

Analysis of how changes affect business processes, workflows, and users.

## [1.2.3] - 2026-01-10

...
```

**Created by**: Manual authoring by release manager or product owner

**Used by**:

- Release approval process (RA pattern)
- Compliance documentation
- Business stakeholders
- Audit trails

**When required**: Primarily for regulated environments (GxP, financial, safety-critical)

## How Modules Link to Changelogs

Module contracts in `.r2r/eac/repository.yml` define where each module's changelog lives.

### Default Path Convention

By default, changelogs use the pattern: `release/<moniker>/CHANGELOG.md`

**Example** (r2r-cli module):

```yaml
modules:
  - moniker: r2r-cli
    name: The CLI of CLIs
    versioning:
      scheme: SemVer
      changelog: release/r2r-cli/CHANGELOG.md # Explicit path
```

If `versioning.changelog` is omitted, the system defaults to `release/<moniker>/CHANGELOG.md`.

### Custom Paths (Relative)

Some modules use relative paths from their component root:

**Example** (ext-eac module):

```yaml
modules:
  - moniker: ext-eac
    name: EAC Extension Container
    versioning:
      scheme: SemVer
    changelog: ../../release/ext-eac/CHANGELOG.md # Relative from containers/ext-eac
    components:
      dockerfile:
        root: containers/ext-eac
```

**Why relative?** When component root is deep in the repository structure (`containers/ext-eac`), a relative path maintains the connection to the centralized `release/` folder.

### Path Resolution in Commands

All release commands resolve changelog paths automatically:

```go
// From go/eac/core/contracts/types.go
func (b *BaseContract) GetChangelog() string {
    if b.Versioning != nil && b.Versioning.Changelog != "" {
        return b.Versioning.Changelog  // Use explicit path
    }
    return "release/" + b.Moniker + "/CHANGELOG.md"  // Default
}
```

**Commands that use this**:

- `r2r release this <module>` - Updates changelog
- `r2r show changelog <module>` - Displays changelog
- `r2r get changelog <module>` - Exports changelog data
- `r2r validate release <module>` - Validates changelog format

You never specify the changelog path manually - commands discover it via module contracts.

## Working with Release Files

### Viewing Changelogs

```bash
# Display full changelog
r2r show changelog r2r-cli

# Display specific version
r2r show changelog r2r-cli 1.2.4

# Display unreleased changes
r2r show changelog r2r-cli unreleased

# Export as JSON
r2r get changelog r2r-cli --as-json
```

### Viewing Release Notes

```bash
# Display latest release notes
r2r show release-notes r2r-cli

# Display specific version
r2r show release-notes r2r-cli 1.2.3
```

### Updating Changelogs

```bash
# Generate changelog entry (analyzes commits)
r2r release this r2r-cli

# Validate changelog format
r2r validate release r2r-cli
```

**What happens**:

1. Command reads module contract to find changelog path
2. Analyzes commits since last release tag
3. Generates entries from conventional commits
4. Updates `release/r2r-cli/CHANGELOG.md`
5. You commit the updated file

## Changelog Format Requirements

Changelogs must follow **Keep a Changelog** format:

### Required Elements

1. **Title**: `# Changelog`
2. **Preamble**: Description and link to Keep a Changelog
3. **Unreleased section**: `## [Unreleased]` for pending changes
4. **Version sections**: `## [X.Y.Z] - YYYY-MM-DD` format
5. **Category subsections**: `### Added`, `### Fixed`, etc.

### Version Ordering

Versions must be in **descending order** (newest first):

```markdown
## [Unreleased]

## [1.2.4] - 2026-01-15

## [1.2.3] - 2026-01-10

## [1.2.2] - 2026-01-08
```

### Date Format

Dates must use **ISO 8601** format: `YYYY-MM-DD`

```markdown
## [1.2.4] - 2026-01-15 ✅ Correct

## [1.2.4] - 2026-1-15 ❌ Wrong (no zero padding)

## [1.2.4] - 01/15/2026 ❌ Wrong (US format)
```

### Validation

```bash
r2r validate release <module>
```

**Checks**:

- ✓ Changelog file exists
- ✓ Valid header format
- ✓ Valid version format
- ✓ Versions in descending order
- ✓ No duplicate versions
- ✓ Valid date format

## Module Examples

### SemVer Module (r2r-cli)

```yaml
moniker: r2r-cli
versioning:
  scheme: SemVer
  changelog: release/r2r-cli/CHANGELOG.md
```

**Changelog location**: `release/r2r-cli/CHANGELOG.md`

**Version format**: `1.2.3` (MAJOR.MINOR.PATCH)

### CalVer Module (docs)

```yaml
moniker: docs
versioning:
  scheme: CalVer
  changelog: release/docs/CHANGELOG.md
```

**Changelog location**: `release/docs/CHANGELOG.md`

**Version format**: `2026.0115` (YYYY.MMDD)

### Container Module with Relative Path (ext-eac)

```yaml
moniker: ext-eac
changelog: ../../release/ext-eac/CHANGELOG.md
components:
  dockerfile:
    root: containers/ext-eac
```

**Changelog location**: `release/ext-eac/CHANGELOG.md` (resolved from `containers/ext-eac`)

**Why relative**: Component root is nested, but changelog stays in centralized location

## Common Patterns

### Finding All Changelogs

```bash
# List all release folders
ls release/

# Find all changelogs
find release -name "CHANGELOG.md"

# Find all release notes
find release -name "RELEASE-NOTES.md"
```

### Checking Module Changelog Path

```bash
# Get changelog path for a module
r2r get modules --as-json | jq '.[] | select(.moniker=="r2r-cli") | .versioning.changelog'
```

### Manual Changelog Entries

You can manually add entries to the `## [Unreleased]` section:

```markdown
## [Unreleased]

### Added

- Manual entry: support for new configuration option

### Fixed

- Manual entry: documentation typo in README
```

When you run `r2r release this <module>`, manual entries are preserved and merged with auto-generated entries.
